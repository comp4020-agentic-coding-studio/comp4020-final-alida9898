# Splitting agents by responsibility

Whether coding work should be split across several agents is a contested question in agentic development. My position is that the failures the critics describe are real, but they come from splitting one task into pieces. When the work is instead split by responsibility, with the shared decisions made in a plan before anything is handed out, each agent given a written boundary, and the results checked by someone who did not build them, a multi-agent setup holds up.

The strongest case against comes from Walden Yan at Cognition (2025): when a Flappy Bird clone is split between one subagent building the pipes and another building the bird, each guesses at what the other assumed and the halves do not fit, because "Actions carry implicit decisions, and conflicting decisions carry bad results." But the bird and the pipes share one screen and one art style. They were one task cut in half, not two independent jobs.

My project, a multi-user 3D clay town, shows a different split. It began as one long conversation where everything "went through one conversation in a straight line, one change after another, and it got messy". Part of the problem, as I wrote then, is that "language is too vague; it cannot express exactly what I mean", and one thread had to hold every meaning at once. Dividing the work was my answer, "because each agent only needs to understand its own part". I then wrote a CLAUDE.md and set up fixed roles (9e3c438): one agent owns camera views, one owns the 3D models, one owns the interface text, and one only checks. Later I stopped the main session from editing code at all. It now writes back its understanding of a request, waits for me to agree, and only then dispatches the work (217558b). In the terms of Schluntz and Zhang (2024), the roles are a form of sectioning, "breaking a task into independent subtasks run in parallel", while the main session acts as an orchestrator that decides each time which roles a request needs. The shape of a model and the camera angle that frames it really are separate jobs, so the agents I ran at the same time were ones whose work could not overlap. Anthropic reached the same rule through experience. Vague instructions led their subagents to duplicate each other and misread tasks, so each subagent now receives "an objective, an output format, guidance on the tools and sources to use, and clear task boundaries" (Hadfield et al., 2025). My CLAUDE.md table records much the same things for each agent: what it owns, what it hands back, and what it must not touch. Because decisions like the art style are settled in the plan and the rules first, no subagent has to guess them.

This position has limits. My boundaries were not right at the start. Seasonal weather and blanket colours were built before any agent owned them, and only afterwards did I add a season agent and redraw the line, leaving it only colours (525e58d). Yan's problem therefore still appears at the edges between roles, which is why the main session keeps the whole picture and a separate checker reviews work it did not write. Some judgements are beyond any checker, though. Anthropic notes that "even in a world of automated evaluations, manual testing remains essential" (Hadfield et al., 2025), but in my experience some things are not merely missed by automation, they cannot be judged by it at all. My rules require the checker to say when a question is about sound, feel or taste, and send spatial adjustments to an editor I use myself rather than describing them to an agent. The cat in my town was finally fixed only when I tuned it myself with sliders and the numbers were copied into the code unchanged (96f789a).

Looking back, I could have done two things better. First, I handed the cat back to myself too late. Face sliders existed from mid-October (d89afe8), yet for weeks I kept asking agents to rebuild its body before giving the body sliders too. I should have asked much earlier which parts of the work no agent could own. Second, independent checking only helps if it finishes and is itself checked. On the last night a server agent reported all 65 tests passing, and one failed when the main session ran them again; a full pre-merge check ran for over an hour and was stopped before it reached a verdict. A checker needs a short list it can finish, and its report needs a second look. Splitting by responsibility worked, but deciding early what stays with me, and keeping the checks small enough to trust, mattered as much as the split itself.
