# Using multiple agents for one project

When I started building my project, a multi-user 3D clay town, everything went through one conversation with Claude Code. Each change came after the last one, and the work got messy. Changing one camera angle could change what another view showed, and it was hard to keep track of what had been decided. I also wanted to work on more than one thing at a time. So I split the work between several agents, each with its own job: one for camera views, one for the 3D models, one for the interface, one for the server, and one that only checks the others' work.

Anthropic describes a similar setup for its research system, where a lead agent breaks a question into parts and hands each part to a subagent (Hadfield et al., 2025). Their first version gave subagents short, vague instructions, and the subagents repeated each other's work or misread the task. Now each subagent gets "an objective, an output format, guidance on the tools and sources to use, and clear task boundaries." I ended up with almost the same thing in my CLAUDE.md. For each agent it lists what the agent is responsible for, what it should hand back, and what it must not touch. The main session does not write code. It writes back what it understood from my request, waits for me to agree, and then passes the work on. Schluntz and Zhang (2024) call this kind of split "sectioning", breaking a task into independent subtasks. I did run some agents at the same time, for example a desktop checker and a phone checker together, but rarely more than four. What helped more than speed was that each agent only had to understand its own part.

Walden Yan at Cognition (2025) argues against splitting work this way. His example is a Flappy Bird clone where one subagent builds the pipes and another builds the bird. Neither knows what the other assumed, so the two parts don't match. He sums it up as "Actions carry implicit decisions, and conflicting decisions carry bad results," and recommends a single agent that keeps all the context. Anthropic also notes that "most coding tasks involve fewer truly parallelizable tasks than research" (Hadfield et al., 2025). I agree with Yan about his example. But the bird and the pipes are part of the same picture and need the same style, so they were never separate jobs. In my project the parts were more separate. How a model is shaped and where the camera stands to look at it are different decisions. Things every agent needs to know, like the art style, were written into the rules before any agent began.

Splitting the work did not remove every problem. The boundaries were not right at first. Weather and seasonal colours were built before any agent was in charge of them, and I added a separate agent for them later. Checking also had limits. Cemri et al. (2025) looked at over 1,600 runs of multi-agent systems and found that verification is one of the three main places they fail. On the last night of this project a checking agent reported that all tests passed, and one of them failed when the tests were run again. Some things an agent could not check at all. Agents rebuilt the cat in my town several times and it still looked wrong. In the end I added sliders and adjusted it myself. Anthropic also says that "even in a world of automated evaluations, manual testing remains essential" (Hadfield et al., 2025). My role was not just to approve what the agents made, but to decide which parts needed my own judgement.

From this project, I think multiple agents work best when the work splits into parts that really are separate, and when the shared decisions are written down before the work is handed out. When a task only looks separable, like Yan's bird and pipes, one agent is probably better. Next time I would decide earlier which parts depend on taste, like how a character looks, and give myself a way to adjust them directly instead of asking agents to try again. I would also keep the checker's list short enough that it can finish, and look again at what it reports.
